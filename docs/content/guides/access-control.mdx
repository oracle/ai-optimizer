AI Optimizer Server authenticates `single_user` and `local_users` deployments through a short-lived Oracle AI Database local end-user connection.

Deployment setup binds one database end user to the reserved `Admin` identity. `Admin` keeps the same application user ID when signing out and back in.

The bare-metal client and all-in-one container initialize the reserved Admin identity during first startup using the application-database password.

## Database account modes

- `single_user` accepts only the mapped Admin account. Member-management routes are unavailable.
- `local_users` lets Admin create member end users, lock or unlock accounts, and issue temporary password resets.

AI Optimizer authenticates managed accounts carrying the configured application login data role.

## Sessions

`POST /v1/auth/login` accepts the managed database username and password and returns an opaque bearer token. Send that token as `Authorization: Bearer <token>` on protected requests. `POST /v1/auth/logout` revokes the current token.

The configured AI Optimizer application database stores only a domain-separated SHA-256 digest of each token. Sessions have absolute and idle expiry, a per-user limit, and bounded cleanup. Account status is cached for at most `AIO_AUTH_ACCOUNT_STATUS_CACHE_SECONDS`; application-mediated account locks and password resets revoke existing sessions immediately across Server instances sharing the same application database.

New and reset member passwords are temporary and expired by Oracle AI Database. Change them with `POST /v1/auth/password-change`; password rules and failure accounting come from the database profile.

Out-of-band password changes leave existing bearer sessions active until logout, idle expiry, or absolute expiry. Out-of-band database account locks are observed after the account-status cache interval.

## Offline Admin recovery

Run `python -m server.app.auth.recovery` from an operator environment with the deployment configuration and direct access to the AI Optimizer application database. For database-account modes, provide `AIO_RECOVERY_ADMIN_DATABASE_USERNAME` and enter the replacement account password at the protected prompt. The command verifies the replacement managed end user, preserves the reserved Admin user ID, revokes existing Admin sessions, and records an audit event. Before restarting, update the mapping in [`AIO_ADMIN_DATABASE_USERNAME`](./env-vars#authentication) or Helm's [`global.authentication.adminDatabaseUsername`](../advanced-guides/k8s-helm#create-a-values-file).

An authenticated Admin can use `PUT /v1/auth/admin/database-mapping` with the current Admin password and replacement managed-account credentials. The operation revokes every Admin session and requires sign-in through the replacement account. Apply the replacement mapping to the deployment configuration before its next restart.
