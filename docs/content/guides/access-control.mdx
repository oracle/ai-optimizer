One **AI Optimizer Server** can serve many GUI sessions, IDE or MCP clients, and external applications. Teams sharing one server use [separate client sessions](../server/multi-user-sessions) to keep conversations and working selections apart while using the same configured resources.

## Choose a Deployment Boundary

- **No Oracle CORE database:** Use the current shared API-key authentication model. It does not provide durable multi-user OIDC isolation.
- **Development:** Configure a CORE Oracle Database with the built-in development OIDC provider. The server binds working sessions and personal artifacts to the authenticated principal.
- **Production eligible:** Configure a CORE Oracle Database with an external OIDC provider, then explicitly select production mode when appropriate.
- **Administrators:** Grant a configured role or scope claim to manage the shared catalog and Deep Data Security resources.

## Client IDs and Access Boundary

In principal-authenticated deployments, `X-AIO-Session` selects an opaque working session after authentication. The server binds that session to its creating principal and rejects access by another principal.

In the no-database shared API-key deployment, the `Client` header and `client`
query parameter retain their current behavior. In a principal-authenticated
deployment, they do not provide access isolation; use `X-AIO-Session` instead.

:::tip
Use client IDs to separate conversation context and client settings. To isolate untrusted tenants, run separate deployments of the **AI Optimizer** with different API keys.
:::

## Shared Catalog Access

The Server is the authority for shared catalog access. The Client does not add a separate password gate.

- **No Oracle CORE database:** `AIO_AUTH_MODE` remains unset and clients use `AIO_API_KEY`. Shared catalog controls are not gated.
- **CORE database with development authentication:** `AIO_AUTH_MODE=dev` is selected by default. The bootstrapped `admin@example.test` identity has the `aio.admin` claim and can manage the shared catalog.
- **CORE database with OIDC or trusted-proxy authentication:** values in `AIO_AUTH_ADMIN_CLAIM_VALUES` identify the principals allowed to manage the shared catalog.

`AIO_CLIENT_PASSWORD` is retired and rejected at Server startup. Use the development admin password only to bootstrap the built-in development identity provider; it does not create a client-side gate.
