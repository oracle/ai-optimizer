AI Optimizer Server authenticates `local_users` deployments through a short-lived Oracle AI Database connection.

Deployment setup binds one database user to the reserved `Admin` identity. `Admin` keeps the same application user ID when signing out and back in.

The bare-metal client and all-in-one container initialize the reserved Admin identity during first startup using the application-database password.

## Database authentication

The Oracle account configured by `AIO_DB_USERNAME` is the reserved Admin and can always sign in. When that account has the required end-user administration privileges, Admin can create member end users, lock or unlock accounts, and issue temporary password resets.

AI Optimizer authenticates members carrying the `AIO_LOGIN_ROLE` data role.

## User settings

Each account has its own persisted model, tool, database, and OCI selections. The same account restores those selections after signing in again. Chat history, embedding jobs, evaluations, and Deep Data Security sessions are scoped to the signed-in account.

## Authorization

Members can use their own settings, chat, history, evaluations, and read-only tools. Admin can also change shared databases, models, OCI profiles, prompts, vector stores, Deep Data Security policy, and deployment settings.

MCP uses the same bearer identity. Read-only MCP capabilities are available to members; database-changing SQLcl capabilities require Admin.

## Sessions

`POST /v1/auth/login` accepts the managed database username and password and returns an opaque bearer token. Send that token as `Authorization: Bearer <token>` on protected requests. `POST /v1/auth/logout` revokes the current token.

The configured AI Optimizer application database stores only a domain-separated SHA-256 digest of each token. Sessions have absolute and idle expiry, a per-user limit, and bounded cleanup. Account status is cached for at most `AIO_AUTH_ACCOUNT_STATUS_CACHE_SECONDS`; application-mediated account locks and password resets revoke existing sessions immediately across Server instances sharing the same application database.

New and reset member passwords are temporary and expired by Oracle AI Database. Members change them with `POST /v1/auth/password-change`; password rules and failure accounting come from the database profile. Admin password changes use database administration so `AIO_DB_PASSWORD` can be updated at the same time.

Out-of-band password changes leave existing bearer sessions active until logout, idle expiry, or absolute expiry. Out-of-band database account locks are observed after the account-status cache interval.

## Admin credential recovery

For `local_users`, recover the `AIO_DB_USERNAME` account using database administration. Update `AIO_DB_PASSWORD`, or the backing Helm database Secret, and restart AI Optimizer. The reserved Admin identity remains unchanged.

For OIDC, run `python -m server.app.auth.recovery` with `AIO_RECOVERY_OIDC_ADMIN_SUBJECT` from an operator environment with the deployment configuration and direct access to the AI Optimizer application database. The command replaces the Admin subject, preserves the reserved Admin user ID, revokes existing Admin sessions, and records an audit event. Set `AIO_OIDC_ADMIN_SUBJECT` to the replacement subject before restarting AI Optimizer.
